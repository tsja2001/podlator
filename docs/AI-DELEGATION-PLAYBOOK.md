# AI 委派开发方法论

> **三角色工作流：人类统筹 → AI 规划 → AI 执行**
>
> 本文件是这套工作流的操作手册。适用于任何需要多阶段、多 AI 协作完成的软件项目。
> 在每次规划和审核工作中，回来读一遍本文件的核心原则。

---

## 1. 角色定义

| 角色 | 典型身份 | 核心职责 | 不做什么 |
|---|---|---|---|
| **统筹者**（人类） | 项目负责人 | 定方向、备资源、审质量、做决断 | 不写代码、不做技术细节决策 |
| **规划者**（Claude） | 架构师 + 项目经理 | 写任务计划书、审完成报告、判断进度 | 不直接写项目代码 |
| **执行者**（AI CLI） | 开发工程师 | 按计划书编码、测试、产出完成报告 | 不做设计决策、遇到歧义停下来 |

**信息流向**：

```
统筹者                 规划者                  执行者
  │                      │                      │
  │──── 需求/方向 ──────→│                      │
  │                      │──── 任务计划书 ──────→│
  │                      │                      │──── 编码+测试
  │                      │←─── 完成报告 ────────│
  │←── 审核结论/下一步 ──│                      │
  │                      │                      │
  │──── 资源准备确认 ───→│──── 下一份计划书 ───→│
```

## 2. 核心原则（7 条）

### 原则 1：计划书是合同，不是建议

计划书写了什么，执行者就做什么。不多做，不少做，不改做。

- 写了"用 `asyncio.Semaphore(5)` 限制并发" → 执行者不应自作主张改成 10
- 写了"mock `get_downloader` 工厂函数" → 执行者不应 mock 更底层的 HTTP
- **没写的东西** → 执行者不要自己加（除非是明显的遗漏，此时应在报告中说明）

**为什么**：这消除了执行者的"自由发挥空间"，避免意外偏离架构方向。

### 原则 2：具体胜过抽象

差的计划：`"实现适当的错误处理"`
好的计划：`"捕获 openai.RateLimitError，包装为 ProviderError(retryable=True)，记录 log.warning"`

- 函数签名比文字描述精确
- 测试用例比需求文档精确
- 代码片段比伪代码精确
- 具体数值比"合理的"精确

**量化清单**（写计划时必检）：
- [ ] 重试次数写了具体数字了吗？
- [ ] 超时秒数写了吗？
- [ ] 输出格式给了例子了吗？
- [ ] 错误处理策略是精确的还是"适当的"？
- [ ] 测试断言是检查具体值还是只检查"非空"？

### 原则 3：测试即规格

测试用例是最不可能被误解的规格。

```python
# 这比任何文字描述都精确：
async def test_retry_stops_after_3_attempts():
    mock_api.side_effect = [RateLimitError, RateLimitError, RateLimitError]
    with pytest.raises(ProviderError, match="Max retries exceeded"):
        await provider.complete("test")
    assert mock_api.call_count == 3
```

**规划者应该**：在计划书中写出关键测试的名称和断言逻辑（不需要完整代码，但需要说清楚"验证什么"）。

**执行者应该**：把计划书中的测试描述当作硬性要求——这些测试必须存在且通过。

### 原则 4：每一步都验证，失败不前进

```
Phase 1 → 验证 → Phase 2 → 验证 → Phase 3 → 验证 → 提交
              ↑失败              ↑失败              ↑失败
              修复               修复               修复
```

**绝不允许**：
- "先写完再统一测试"（bug 会叠加到无法调试）
- "这个测试偶尔失败，跳过它"（flaky = bug）
- "覆盖率差一点，先过了"（差的那一点通常是 error handling 路径）

### 原则 5：完成报告是唯一的进度凭证

不接受"我做完了"的口头宣告。只看完成报告中的：
- `uv run pytest -v` 的完整输出（不是截图，是文本）
- 覆盖率数字
- ruff + mypy 的输出
- 文件变更清单

**规划者审核时的红旗信号**：
- 测试名全是 `test_xxx_works`、`test_xxx_success`，没有失败/边界用例 → 测试质量不足
- 覆盖率高但测试数量少 → 可能是空测试凑覆盖率
- "已知问题"列了接口变更但没解释为什么 → 可能偏离了架构
- 测试输出中有 warning 被忽略 → 可能隐藏 bug

### 原则 6：资源准备在前，执行在后

执行 AI 启动后不应该被"缺东西"阻塞。每份计划书必须有：

1. **前置条件清单**（上一阶段完成了吗？）
2. **资源准备清单**（API Key？测试数据？磁盘空间？）
3. **预检命令**（一键验证所有准备就绪）

**统筹者的工作**就是在计划书交给执行者之前，把前置条件和资源清单全部勾掉。

### 原则 7：不要提前规划太细

> "计划赶不上变化" — 但这不是不做计划的理由，而是不要做太远的计划。

- **当前任务**：写到文件级、函数级、测试用例级
- **下一个任务**：写到模块级、接口级
- **更远的任务**：只写目标和准备清单

因为每个任务的实际实现都可能调整接口和数据结构，太细的远期计划会变成过时的误导。

## 3. 计划书编写规范

### 3.1 结构模板

```markdown
# M<里程碑>.<序号> — <标题>

## 前置条件
- [x] 已完成的
- [ ] 需要确认的

## 预检命令
（一键脚本，验证环境就绪）

## Phase N: <名称>
### N.1 <具体步骤>
（文件路径、函数签名、代码片段、关键逻辑说明）
### Phase N 验证
（必须通过的命令）

## 最终验证
## Git 提交
## 完成报告
```

### 3.2 关键细节检查项

写完计划书后自查：

- [ ] 每个新文件都写了文件路径？
- [ ] 关键函数给了签名（参数名+类型+返回类型）？
- [ ] 每个外部 API 调用说了怎么 mock？
- [ ] 每个测试说了断言什么（不只是"写个测试"）？
- [ ] 错误处理策略是具体的（哪些异常、怎么包装、retryable?）？
- [ ] 有没有依赖尚未实现的代码？如果有，是否说明了 mock/stub 策略？
- [ ] 前置条件是否列全了（上一步完成 + 资源就绪）？

### 3.3 给执行者的"防呆"设计

1. **开头显眼位置**放"执行前先读 EXECUTION-FRAMEWORK.md"
2. **预检失败 = 停止**，写在前面不要藏
3. **每个 Phase 结尾有验证命令**，不通过不继续
4. **明确说"不要做什么"**（如"M1 先不做依赖注入重构，用直接创建 Settings 的方式"）
5. **提供故障排除指南**（常见错误 + 解法）

## 4. 完成报告审核协议

### 4.1 审核清单（规划者用）

收到完成报告后，按以下顺序审核：

**第一遍：快速扫描（1 分钟）**
- [ ] 状态是 ✅ 还是 ⚠️/❌？
- [ ] pytest 输出中有没有 FAILED 或 ERROR？
- [ ] 覆盖率数字达标吗？
- [ ] ruff/mypy 有报错吗？

**第二遍：测试质量（3 分钟）**
- [ ] 测试名称是否描述了具体行为？（`test_transcribe_falls_back_on_timeout` ✅ vs `test_transcribe` ❌）
- [ ] 失败场景覆盖了吗？（至少有 `_error`、`_timeout`、`_invalid` 后缀的测试）
- [ ] 计划书中要求的关键测试是否都存在？

**第三遍：偏差检查（2 分钟）**
- [ ] "已知问题"部分为空或只有不影响后续的小问题？
- [ ] 文件变更清单与计划书预期一致？没有意外的新文件或删除？
- [ ] 接口是否有未预期的变更？

**审核结论**：
- **通过** → 产出下一个任务计划书
- **有条件通过** → 列出必须修复的项，执行者修复后重新提交报告
- **不通过** → 说明原因，要求重做（极端情况 git reset）

### 4.2 常见审核发现及处理

| 发现 | 严重度 | 处理 |
|---|---|---|
| 测试全是正路径，无失败测试 | 高 | 打回，补充失败测试 |
| 覆盖率达标但测试数量明显偏少 | 中 | 检查是否有空断言 |
| 接口签名变了但报告没提 | 高 | 打回，要求说明原因并更新文档 |
| Smoke 测试跳过（无 API Key） | 低 | 提醒统筹者配置 Key |
| 一个"已知问题"涉及核心接口 | 高 | 当场修复，不允许带着进下一阶段 |
| 日志中有 print() 残留 | 中 | 打回修复 |

## 5. 统筹者操作指南

### 5.1 每个里程碑的固定流程

```
1. 告诉规划者"开始规划 M<x>"
2. 规划者产出：
   - 任务计划书（1-3 份）
   - 用户准备清单
3. 按清单准备资源（API Key、测试数据等）
4. 确认准备完毕
5. 把计划书交给执行者
6. 执行者产出完成报告
7. 把完成报告转给规划者审核
8. 审核通过 → 回到步骤 1（下一个里程碑）
   审核不过 → 执行者修复 → 回到步骤 6
```

### 5.2 什么时候需要人类介入

| 信号 | 行动 |
|---|---|
| 规划者说"这个需要你决定" | 做产品决策（如 Prompt 措辞、UI 布局） |
| 执行者报告"API Key 无效" | 检查并更新 .env |
| 完成报告状态为 ❌ | 与规划者讨论是修复还是回滚 |
| 连续两次审核不通过 | 可能是计划书有问题，与规划者重新讨论方案 |
| Smoke 测试的输出质量不满意 | 与规划者讨论 Prompt 调优方向 |

### 5.3 什么时候不需要人类介入

- 执行者在 Phase 验证中发现小 bug 并自行修复 → 正常，不用管
- 规划者在审核中要求执行者补测试 → 正常流程
- 执行者报告"依赖 X 版本冲突，已调整" → 只要测试通过就行
- 覆盖率从 72% 提到 75% 的优化 → 让 AI 之间自行处理

## 6. 防坑要点速查

### 6.1 计划书阶段

| 坑 | 防法 |
|---|---|
| 规格模糊，执行者理解偏差 | 用代码片段和测试用例代替文字描述 |
| 漏了前置条件 | 自查清单：API Key？磁盘空间？上一步完成？网络？ |
| 远期计划写太细，实际执行时已过时 | 只细化当前+下一个任务，更远的只写目标 |
| 没写"不要做什么" | 显式写出限制（"M1 先不做 XXX 优化"） |
| 假设执行者知道背景 | 计划书必须自包含，不依赖对话上下文 |

### 6.2 执行阶段

| 坑 | 防法 |
|---|---|
| 执行者跳过验证继续下一个 Phase | 计划书每个 Phase 末尾有强制验证命令 |
| 执行者静默改了接口 | 完成报告要求列出所有文件变更 |
| 测试质量注水 | 计划书中写明关键测试的断言内容 |
| 依赖安装失败卡住 | 计划书附故障排除指南 |
| 执行者在一个问题上死磕太久 | 完成报告中可标 ⚠️ 说明跳过原因 |

### 6.3 审核阶段

| 坑 | 防法 |
|---|---|
| 只看"通过/失败"不看测试质量 | 审核时必须读测试名列表 |
| "已知问题"被轻易放过 | 涉及接口/核心逻辑的问题零容忍 |
| 完成报告格式不统一难以对比 | 强制使用标准模板 |
| 技术债累积到下一个里程碑爆发 | 每个任务的"已知问题"必须在该任务内关闭 |

## 7. 模板速查

### 给规划者的启动 Prompt

```
我需要你为 [项目名] 规划 M<x> 的执行计划。

当前状态：
- M<x-1> 已完成，完成报告：[粘贴或引用]
- 代码库路径：[路径]
- 关键文档：CLAUDE.md, docs/ARCHITECTURE.md, docs/ROADMAP.md

请产出：
1. M<x> 的子任务计划书（按 EXECUTION-FRAMEWORK.md 格式）
2. 用户准备清单（我需要提前做什么）
3. 审核用的关键验证点
```

### 给执行者的启动 Prompt

```
请先阅读以下文件（按顺序）：
1. docs/tasks/EXECUTION-FRAMEWORK.md — 通用执行协议
2. CLAUDE.md — 项目规范（重点第 7、9、13 章）
3. docs/tasks/M<x.y>-<name>.md — 本次任务计划书

然后按计划书逐 Phase 执行。每个 Phase 结束后运行验证命令。
全部完成后按 EXECUTION-FRAMEWORK.md 第 6 节格式输出完成报告。
```

### 给规划者的审核 Prompt

```
请审核以下完成报告，判断 M<x.y> 是否可以标记为完成。

完成报告：
[粘贴]

审核标准参考 docs/AI-DELEGATION-PLAYBOOK.md 第 4 节。
重点检查：测试质量、接口偏差、已知问题的影响。
```
