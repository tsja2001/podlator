# 目标:把三个英文播客做成「抖音中文剪辑解说稿」

## 一句话目标

参考已有的黄仁勋播客「抖音中文剪辑解说稿」(黄金样本),为 `project/` 下另外**三个**英文播客各产出一篇**同等水准**的中文解说稿。
**产出必须由可复用的代码 + CLI 驱动,不允许在对话里手工把字幕翻译/改写成稿子。**

---

## 背景与动机

- 原始素材是**全英文、很长**的访谈 SRT,听和读都很费劲。
- 抖音上的中文剪辑版**有观点、有解说、听着舒服**——这是要对标的「黄金样本」,不是简单翻译,是**二次创作/解说**。

**参考样本(先读透):**

- 黄金样本(产出要长成这样): `project/英伟达黄仁勋播客/抖音剪辑版/抖音剪辑黄仁勋访谈口播稿_分段整理版.md`
- 它对应的原始英文字幕(用来对照"原文→解说"发生了什么转化): `project/英伟达黄仁勋播客/原版/01-0原版英文字幕.srt`

**要处理的三个播客(都在 `project/` 下,纯英文、无说话人标注;注意路径里的空格):**

1. `project/ 迈克尔·尼尔森——为何外星文明的技术栈将与我们不同/ 迈克尔·尼尔森——为何外星文明的技术栈将与我们不同.srt` ⚠️ 文件夹名和文件名都有**前导空格**
2. `project/马斯克如何把 1 太瓦 GPU 送上太空 /马斯克如何把 1 太瓦 GPU 送上太空 .srt` ⚠️ 文件夹名和 `.srt` 前有**尾随空格**
3. `project/Casey Handmer中国将赢得通用AGI竞争/Casey Handmer中国在能源领域正超越美国这是否意味着他们将赢得通用AGI竞争` ⚠️ **没有 `.srt` 扩展名**,但内容就是标准 SRT,处理前先确认并按 SRT 解析

---

## 黄金样本的特征(这就是验收标尺,动手前先研究透)

精读样本后会发现,它和逐字翻译的差距在于以下几点,你的产出必须命中这些:

1. **钩子开场**:不从访谈第一句开始,而是用一个戏剧化场景抓人(样本开篇是"黄仁勋被怼上头发火")。
2. **解说者第一人称视角**:有"我也挺喜欢看他节目"这类主观口吻和态度,不是中立旁白。
3. **按主题/论点重组,而非线性复述**:样本把访谈重组成"四大赌注"(供应链锁死、ASIC/TPU 竞争、对华出口管制、产能天花板),不是顺着时间轴翻译。
4. **术语白话化**:commodity、fabless、HBM、CoWoS、token 等都被翻译成大白话并举例解释。
5. **穿插外部背景知识**:主动补充《芯片战争》、ASML/EUV 历史、Joe Rogan 类比等访谈里没有的内容来增强可信度和可读性。
6. **口语化、有节奏**:短句、设问、"你想想""说白了"这类口头禅,适合口播。

> 第一阶段产出物就是把上面这些**写成一份可执行的「风格规范 / prompt 蓝图」**,后面所有生成都围绕它。

## 关键约束(必须遵守,违反即不合格)

1. **产出靠代码,不靠手搓**:开发**可复用的节点 + CLI 命令**来跑,Claude 不在对话里直接翻译/改写字幕。最终要能用 CLI 对任意一个新 SRT 重跑出稿子。

2. **优先复用项目已有资产 —— 别重造轮子(原稿最易忽略的一点):**
   - 本项目已是 **LangGraph pipeline**,且 `src/podlator/cli.py` **已有这些命令**,先盘点它们做到了什么程度,能复用就复用、能扩展就扩展,缺什么才新建:
     - `parse-srt` —— 解析 SRT
     - `assign-speakers` —— **说话人分离(就是你说的"分片用大模型处理"那一步,已经有了)**
     - `split` —— 章节/内容分段
     - `transcribe` / `render` / `polish` 等
   - 节点在 `src/podlator/graph/nodes/`、prompt 在 `src/podlator/prompts/`、provider 抽象在 `src/podlator/providers/`,新增能力按同样模式来。
   - ⚠️ 注意:现有 `render`/`polish` 产出的是**简报**风格,和"抖音解说稿"是两种文体,**解说稿生成大概率要新增节点 + prompt + 命令**,这才是本目标真正的新工作量。

3. **遵守项目铁律(见 `CLAUDE.md`)**:TDD 优先、结构化日志(structlog,禁 print)、provider 抽象、约定式提交,完成后逐项过 **DoD 自检清单(第 13 章)**。

4. **先新建分支再动手。**

## 执行思路(分阶段,做完一段验证一段,别一口气全做完)

0. **准备**:新建分支;确认三个输入文件能正确读取(尤其 Casey 那个无扩展名文件)。
1. **吃透样本**:对照黄金样本 ↔ 它的原始英文 SRT,搞清楚"逐字稿 → 解说稿"具体发生了哪些转化,产出上面那份**风格规范 / prompt 蓝图**。
2. **说话人分离**:用/扩展 `assign-speakers`,对长 SRT 分片调大模型标注说话人(访谈通常 ≥2 人)。**先拿黄金样本的原版 SRT 验证**——它有已知的剪辑版可对照,准不准一眼能看出来。
3. **内容分段 + 主题重组**:在 `split` 基础上,按"论点/主题"聚合重组(对标样本的"四大赌注"结构)。
4. **解说稿生成(核心新能力)**:新增节点 + prompt + CLI 命令(如 `douyin-script`),把分好段的中文内容改写成解说稿——命中"黄金样本特征"那 6 条。
5. **串成流水线**:能用一条命令(或一个 pipeline)从一个 SRT 一路跑到最终 `.md`。
6. **对照优化**:三篇产出逐项对比黄金样本,找差距、迭代 prompt 和流程。

## 测试要求(强制 —— 每个阶段的 CLI 都要有详细用例)

> 遵循 `CLAUDE.md` 第 9 章测试矩阵:LLM 调用一律 **mock**(unit 层禁打真实 API),真实 API 验证放 smoke 层、可选跳过。
> **唯一例外:语音转文字 `transcribe` CLI 本目标不需要新增测试。** 其余每个 CLI 都必须覆盖「正常路径 + 1 个失败路径 + 1~2 个边界条件」:

| CLI | 正常路径 | 失败路径 | 边界条件 |
|---|---|---|---|
| `parse-srt` | 标准 SRT 解析出正确条目 | 畸形 SRT(时间轴错乱/缺空行) | 空文件;**无 `.srt` 扩展名但内容是 SRT**(Casey 那种) |
| `assign-speakers`(说话人分离) | 多说话人正确标注(mock LLM 返回) | LLM 返回非法/超时 → 重试或报错 | 单说话人;**分片边界处说话人连续性**(同一人被切到两片不能变成两个标签) |
| `split`(分段/主题重组) | 按主题正确聚合分段(mock LLM) | LLM 返回空/格式错 | 超短输入(1~2 段);超长输入(触发分片) |
| `douyin-script`(解说稿生成,新增) | 生成稿命中风格规范要素 | LLM 失败 → 重试/降级 | 空输入;超长输入分片 |
| 串起来的 pipeline | 一个 SRT 一路跑到 `.md`(全程 mock LLM) | 中途某节点失败的处理 | —— |

补充硬性要求:

- **每新增/扩展一个 CLI,先写测试再写实现**(TDD,`CLAUDE.md` 第 3 章)。
- 测试用 `tmp_path`、`pytest-httpx`(mock HTTP)、`monkeypatch`,**不读写真实文件系统、不打真实 API**。
- 放一份小的 SRT fixture 到 `tests/fixtures/`(从样本截 30~60 秒即可),供各 CLI 测试复用。
- 新增代码覆盖率 ≥ 80%,核心节点 ≥ 85%。

## 遇到困难怎么办

- **样本风格难复刻** → 先把"风格规范"写细,再用小样本试 prompt,迭代逼近,别指望一次到位。
- **说话人分离不准** → 回到黄金样本的原版 SRT 上调(有已知答案可对照),调准了再用到三个新播客。
- **拿不准产品措辞**(解说口吻、观点尺度、术语翻译) → 这是产品决策,**停下来问用户**,别自己拍板。
